## Attack 1 — carry correctness for k>2 (highest priority)

**PASS — and the gap is now closed, not just argued.**

### 1a. Is k>2 guaranteed by the parametric construction? YES — structural argument

`tk_add_gates_n(m)` (`instr.rs:246`) is *manifestly uniform in m*: every loop body
is identical across widths; the only width-dependent artifacts are the loop bounds
and the two explicit top-wire gates (`a(m-1)/a(m-2)`). There is **no reference to
`W` or any byte boundary anywhere in the generator** — "byte boundaries" do not
exist at the wire level, so there is no code path that could behave differently at
a boundary. A k≥3-only bug would require the generator to emit something different
at larger m; it structurally cannot.

I verified this is not just an appeal to symmetry by re-deriving the TK invariant
for the *exact emitted gate list* at arbitrary m (phases numbered in emission
order; `a` = operand wires m..2m, `b` = target wires 0..m, `c_0=0`,
`c_{i+1}=maj(a_i,b_i,c_i)`, `s_i = a_i⊕b_i⊕c_i`):

1. Phase 1 (`b[i]^=a[i]`, i=1..m−2): `B[i]=a_i⊕b_i`; note `b[0]` and `b[m−1]`
   intentionally untouched.
2. Phase 2 (descending `a[i+1]^=a[i]`): each target reads the ORIGINAL `a[i]`
   (descending order is what makes this true) → `A[j]=a_j⊕a_{j−1}` for j=2..m−1.
3. Phase 3 (ascending Toffolis `a[i+1]^=a[i]&b[i]`): induction — if
   `A'[i]=a_i⊕c_i` and `B[i]=a_i⊕b_i`, the product is
   `(a_i⊕c_i)(a_i⊕b_i) = a_i⊕c_{i+1}`, so `A'[i+1]=a_{i+1}⊕c_{i+1}`. Base i=0:
   `a_0·b_0 = c_1` (works precisely BECAUSE `b[0]` skipped phase 1 and `c_0=0` —
   the one asymmetric boundary, and it is handled).
4. Phases 4–5: `b[m−1]^=a[m−1]` gives `s_{m−1}` ✓; the Toffoli then returns
   `a[m−1]` to its phase-2 state.
5. Phase 6 (descending `b[i]^=a[i]; a[i]^=a[i−1]&b[i−1]`): at step i, `b[i−1]` has
   NOT yet been rewritten (descending order again) so the Toffoli reads the
   phase-1/phase-3 values and returns `a[i]` to its phase-2 state; `b[i]` becomes
   `b_i⊕c_i`.
6. Phase 7 (ascending `a[i+1]^=a[i]`): ascending order undoes descending phase 2
   using already-restored lower wires → all `a` bit-identical to input
   (zero-ancilla at the operand level, exactly as claimed).
7. Phase 8 (`b[i]^=a[i]`, i=0..m−2): `b_i⊕c_i⊕a_i = s_i` ✓ (`b[m−1]` was finished
   in phase 4).

Every boundary case (`b[0]`, the top two wires, the two order-sensitive sweeps) is
width-independent. Nothing in the induction step mentions m. Verified degenerate
m=2 by hand as well (all interior loops empty; still correct).

The remaining k-dependent code is the *plumbing*: `flatten(pair_ty)` and
`gate_at`'s bubble routing at wire indices up to 2m−1 (`plumbing.rs:141`). That is
recursive, index-uniform code — and it is exercised symbolically-completely at
m=8/16/24/32 (below) and concretely at m=40/64.

## Attack 2 — net-zero routing scratch

**PASS.**

- "Zero-ancilla" at the operand level is exact (phase 7 of the induction above:
  the reverse sweep restores every operand wire — no garbage, no bracket).
- The cell-lowering routing scratch is not per-input luck: the lowering's MCNOT
  emission is *structurally* ancilla-clean per instance (ADR-0040: K1 AND-chain,
  one R1, self-inverse chain replayed in reverse — `lower.rs:695-712`, "restores
  every ancilla to its init on every input"). A-7.1 adds no new cell kinds
  (`wide_add_netlist_valid_and_conservative` pins K0..K2+R1), so net-zero is
  inherited from the production lowering, the same machinery `pc_add_br` and the
  whole CPU already stand on.
- The shipped balanced-simulate test checks **all** netlist outputs (data vs eval
  AND every ancilla bit vs its init) — I confirmed `lower_with_ancillas` emits
  outputs as exactly [data..., ancilla...] so no output escapes the check.
- Gap I probed: the shipped 8 sample vectors omit the max-carry input
  `0xFFFF+0xFFFF` (every carry = 1, every Toffoli fires). Review probe P4 ran
  balanced-netlist `simulate` at k=2 AND k=3 on `(m,m)` all-ones, wrap, and
  top-boundary ripple, asserting `outputs.len() == n_data + n_ancilla` and every
  ancilla restored — **PASS (20 s), no leaked wire found.** (Worth noting the
  shipped 8-vector list could cheaply add `(0xFFFF,0xFFFF)`.)
- Ancilla profile: k=1 count == `pc_add_br` exactly; +16/byte fixed increment
  (pinned parametrically in the shipped suite).

## Attack 3 — adjoint = exact wide subtract

**PASS.**

`Iso::sym` is the structural adjoint (`theseus-core/src/adjoint.rs`): reverses
`Seq`, self-inverse CNOT/Toffoli prims map to themselves — `wide_sub(k)` is
literally the gate-reversed circuit, so `sub∘add = id` is compositional, and the
BDD equivs above prove `add` is exactly `+`; a bijection's unique inverse is
therefore exactly `−`. Empirically: shipped default-tier roundtrips (k=1 strided
fast; strided k=2; focused k=4 — all green in the review's release run of the
suite; the k=1 *exhaustive* roundtrip is subsumed by the complete k=1 BDD equiv +
the standalone m=8 exhaustive gate-sim, see probe log) plus review probe P3
roundtrips at k=3 and k=8 on max-carry vectors, including direct
`sub == (a−b mod 2^8k, b)` value checks. Borrow-across-byte (`0x0100−0x0001=0x00FF`
class) is covered by the strided sets (e.g. `(0x00FF,0x0001)` roundtrip forces the
borrow on the way back). All pass.

## Attack 5 — byte-order / value-model consistency

**PASS with one MINOR finding.**

- Convention shipped: `wide_word_ty(k)` = right-nested `Prod` of `word8()`s,
  FIRST component = LSB byte; `flatten` is depth-first so wire 0 = LSB bit of the
  LSB byte. This matches the IR precedent exactly (`types.rs:264 push_ir_bits`,
  IR_b0 first = LSB byte first) — the convention the design doc (§8) told us to pin.
- The convention is *genuinely* pinned — but not by the test named for it. The
  carry-direction tests are what pin it: `0x00FF + 1 = 0x0100` under the helpers'
  LSB-first marshaling can only pass if wire 0 is the LSB and the first component
  is the low byte (a flipped convention would ripple the carry the wrong way).
- **MINOR-1 (pin vacuity):** the endianness assertion inside
  `wide_word_ty_and_byte_order_pin` — "add 0 to 0x0201 and read back" — is
  vacuous for byte order: any self-consistent encode/decode round-trips a
  carry-free add regardless of which byte lands in which register. If a future
  refactor flipped both helpers together, this named pin would still pass (the
  carry tests would catch the semantic break, but the *pin* would be lying about
  what it pins). Suggested regression: assert the flattened bit positions
  directly — e.g. `bits_of(wide_add_input_value(2, 0x0201, 0))[0..8] == bits of
  0x01` — which fails under a flip with no carry involved.
- A-7.0 interaction: none today — A-7.0's wide-bitwise slice uses a byte-LANE
  interleaved layout (`Prod(Prod(a0,b0),Prod(a1,b1))`) where endianness is
  irrelevant (lanes independent), and `wide_add` is not yet wired to any
  `Prod(Flat(8),…)` marshaling. The convention collision surface arrives with
  A-7.2 (wide Add reduce over program values) — that slice MUST cross-pin
  `value_to_leaf_bytes` leaf order against `wide_word_ty` byte order. Flagged for
  the A-7.2 spec, not a defect in A-7.1.

## Attack 6 — verification-tier honesty

**PASS with two MINOR findings.**

- **Is balanced-`simulate` the right authority (vs `run_on_cpu`)?** Yes, and the
  test file argues it honestly: `wide_add` is a gate-level operand iso, not an ISA
  instruction — it is unreachable from any ROM, so there is nothing for the
  ISA/`run_on_cpu` path to run. `lower → balance → simulate` is the same physical
  tier `step_faithfulness_balanced_simulate` uses for the CPU step itself — and
  unlike that (RAM-`#[ignore]`d) precedent, the wide_add instance RUNS in the
  default tier. When A-7.2 wires wide arithmetic into compiled programs, the full
  L19 `run_on_cpu == eval` ring authority becomes applicable and mandatory —
  again an A-7.2 gate, not an A-7.1 gap.
- **MINOR-2 (wording):** the test header calls tier 1 "walk the compiled iso
  *netlist* symbolically". `eval_bdd` (`bveq_netlist.rs:290`) is a symbolic
  interpreter of the **Iso term** (structural recursion mirroring
  `theseus_eval::eval`, prims via truth tables) — it never sees the lowered cell
  netlist. The complete-domain BDD proof is therefore *Iso ≡ spec*; *netlist ≡
  Iso* rests on the (sampled) balanced-simulate tier plus the production-lowering
  invariants. That trust structure is fine and matches precedent — but the
  comment overstates what tier 1 covers. Suggest s/netlist/term/ so a future
  reader doesn't skip the simulate tier believing the BDD proof covered lowering.
- **`#[ignore]` inventory is honest:** the three ignored tests (k=4 BDD, k=1
  exhaustive exec, k=1 exhaustive roundtrip) are all *redundant extra* tiers —
  every claim has a default-tier witness. Nothing load-bearing is ignored-only.
  The k=4 BDD was executed by this review and passes (4.52 s); the two k=1
  exhaustives were started but not run to completion (see MINOR-3 — they are far
  slower than labeled), and their content is independently covered by the
  complete k=1 BDD + the standalone exhaustive m=8 gate-sim.
- **MINOR-3 (CI cost / inaccurate ignore-label timings):** all three
  `#[ignore]` reasons carry timing claims that do not reproduce on this host,
  in *both* directions:
  - k=4 BDD "slow": actually **4.52 s in release**. It is slow only because
    `biodivine-lib-bdd` has no dev-profile opt override (workspace `Cargo.toml`
    pins opt-level 2 for theseus-core/eval/netlist but NOT the BDD crate), so
    the walk runs at opt-level 0.
  - k=1 exhaustive exec "~90 s" and roundtrip "~180 s": a release-build run of
    the suite with these included was still going after **>30 min wall /
    1 CPU-hour** (the helpers rebuild `wide_add(k)` and re-run `type_of` per
    vector — 2^16 × several term re-derivations). In the dev profile these
    labels are off by well over an order of magnitude.
  - Also observed: the *default* dev-tier suite ran 17+ min / ~30 GB RSS on
    this host (the k=2 BDD walk is the hog) — worth knowing before wiring it
    into any gate (cf. the maestro no-gate-timeout lesson).
  Suggested follow-ups: add `[profile.dev.package.biodivine-lib-bdd]
  opt-level = 2`; **un-ignore the k=4 BDD test** (the strongest single piece of
  evidence in the file currently runs nowhere by default); hoist the
  `wide_add(k)`/`type_of` construction out of the per-vector helpers so the
  exhaustive tiers cost what their labels claim.
